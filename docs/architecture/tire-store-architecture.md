# معماری پیشنهادی فروشگاه تایر

## هدف

فروشگاه تایر فعلاً بخشی از اپ راننده است، اما Backend آن مستقل طراحی می‌شود تا در آینده وب‌سایت یا PWA مستقلی با UI جدید نیز از همان Backend استفاده کند.

```text
اپ راننده ────────────┐
                      ├── TireStore API ─── TireStoreDb
فروشگاه مستقل آینده ──┘         │
                                └── ERP API
```

## مرزبندی سیستم‌ها

### ERP

ERP همچنان مسئول اطلاعات و هویت راننده، سفرها، عملیات لجستیکی، وضعیت راننده، اعتبار مرجع و Login فعلی اپ راننده است.

ERP از Microsoft SQL Server و دیتابیس اصلی `NaraApplicationDb` استفاده می‌کند.

### فروشگاه تایر

Backend فروشگاه مسئول این بخش‌هاست:

- فروشگاه‌ها
- کاربران و دسترسی‌های هر فروشگاه
- محصولات، قیمت و موجودی
- سفارش‌ها و اقساط
- پنل مدیریت فروشگاه

فروشگاه دیتابیس مستقل خود با نام پیشنهادی `TireStoreDb` را خواهد داشت.

## کاربران فروشگاه

Tenant سیستم خودِ `Store` است. هر فروشگاه کاربران و دسترسی‌های خودش را دارد.

نقش‌های اولیه:

- `PlatformSuperAdmin`: مدیریت کل پلتفرم و فروشگاه‌ها
- `StoreAdmin`: مدیریت کاربران و اطلاعات فروشگاه خودش
- `StoreOperator`: مدیریت عملیات و سفارش‌ها
- `StoreFinance`: مشاهده امور مالی و اقساط
- `StoreViewer`: دسترسی خواندنی

دسترسی‌های فروشگاه در Store Backend مدیریت می‌شوند و به سیستم دسترسی ERP وابسته نیستند.

## ارتباط با ERP

فروشگاه از طریق API اطلاعات ضروری راننده، وضعیت راننده و اعتبار را از ERP دریافت می‌کند. هنگام خرید قسطی نیز رزرو و تأیید اعتبار از طریق ERP انجام می‌شود.

برای نمایش سریع می‌توان خلاصه اطلاعات موردنیاز راننده را در Store Database نگه‌داری و با ERP همگام کرد، اما اطلاعات اصلی راننده و اعتبار همچنان متعلق به ERP است.

## Frontend

در فاز فعلی، فروشگاه به‌صورت یک Feature مستقل داخل Frontend اپ راننده پیاده می‌شود:

```text
src/features/tire-store/
```

این Feature فقط از `TireStore API` استفاده می‌کند. Frontend مستقل آینده نیز همان API را مصرف خواهد کرد؛ بنابراین منطق سفارش، اعتبار، موجودی و اقساط دوباره نوشته نمی‌شود.

## ساختار Backend

برای تیم فعلی، یک Modular Monolith کافی است:

```text
TireStore.Api
├── Stores & Users
├── Catalog & Inventory
├── Orders
├── Installments
└── ERP Integration
```

در فاز فعلی نیازی به Microservice یا Message Broker نیست. در صورت افزایش مقیاس، ماژول‌ها بعداً قابل جداسازی خواهند بود.

## مسیر اجرا

### فاز اول

- ایجاد `TireStoreDb`
- جایگزینی `InMemoryStore` با EF Core و SQL Server
- اضافه کردن فروشگاه، کاربران، نقش‌ها و دسترسی‌ها
- انتقال محصولات، سفارش‌ها و اقساط به دیتابیس واقعی

### فاز دوم

- اتصال Backend فروشگاه به APIهای راننده و اعتبار ERP
- اتصال Feature فروشگاه در اپ راننده به `TireStore API`
- اتصال پنل مدیریت فروشگاه به داده‌های واقعی

### فاز سوم

- ساخت Frontend مستقل با UI جدید
- استفاده از همان Backend و قراردادهای موجود
- تکمیل گزارش‌ها و کنترل‌های عملیاتی

## تصمیم نهایی

فروشگاه از نظر UI فعلاً ادامه اپ راننده است، اما از نظر Backend و Database یک سیستم مستقل است.

این معماری نسخه فعلی را سریع‌تر قابل تحویل می‌کند، اپ راننده را نیازمند بازنویسی نمی‌کند و امکان ساخت فروشگاه مستقل آینده با همان Backend را حفظ می‌کند.
